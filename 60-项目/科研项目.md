# 科研项目

## 05:00：自动化专业科研实践项目推荐

每天选择一个适合自动化专业本科二、三年级开展的公开 GitHub 项目或代码库，写明它能回答的具体问题、完成边界、前置知识、可复现实验与验收产出。项目推荐不把“仓库存在”写成“研究结论已成立”：涉及性能、创新性或许可证的判断须标记核验状态。

每条推荐直接写在本页，使项目、问题、实验设计和验收标准在打开笔记时即可阅读。每条至少包含可靠来源、一个可检验的研究问题、可比较的对照和可交付成果。

## 2026-10-05｜小车路径跟踪与前视距离研究

推荐项目：[AtsushiSakai/PythonRobotics](https://github.com/AtsushiSakai/PythonRobotics) 的 [Pure Pursuit 路径跟踪示例](https://github.com/AtsushiSakai/PythonRobotics/blob/master/PathTracking/pure_pursuit/pure_pursuit.py)。本次只建议研究一个清晰问题：在不同车速和路径弯曲程度下，前视距离的选取如何影响小车的横向跟踪误差与转向平滑性？2026-10-05 已读取仓库 README、`PathTracking` 目录和该源码；项目本身尚未在本机运行。

![PythonRobotics 的 Pure Pursuit 路径跟踪动画（仓库维护者提供的官方 GIF 库）](https://github.com/AtsushiSakai/PythonRoboticsGifs/raw/master/PathTracking/pure_pursuit/animation.gif)

上图来自该项目 README 明确指向的 `PythonRoboticsGifs` 官方配套仓库，用于展示参考路径与车辆轨迹，不作为任何性能结论的证据。

Pure Pursuit 依据前方目标点计算转向，示例还用比例控制调整速度。源码已有速度相关规则 $L_f=kv+L_{fc}$，所以不能把“速度相关前视距离”当作新贡献。可比较三种规则：固定前视距离、仓库原有的速度规则，以及自己提出的“速度与路径曲率联合”的候选规则。第三种是否更好必须由实验决定。

建议先用 4--6 周完成仿真。第一周跑通例程并理解状态更新；第二周保存轨迹与控制量，统一计算指标；第三周扫描原规则参数；第四周实现候选规则并作同条件比较；最后加入初始偏差或噪声并写短报告。需要 Python、向量与距离、三角函数和基础反馈控制；第一阶段普通电脑即可，不需要实体小车或 STM32。

实验中必须固定参考路径、初始状态、运动模型、时间步长、目标速度和转向限幅；调参路径与评价路径分开。至少在直线、缓弯、急弯和 S 弯上报告横向误差均方根、最大误差、转向变化幅度、完成率和实际速度。横向误差应定义为车辆后轴中心到参考折线的最短距离，不能误用到前视目标点的距离；未完成路径的样本应单列报告。

验收成果是可复现实验代码、参数配置、轨迹图、误差图、指标表，以及说明优势与失效条件的短报告。仓库 README 标示 MIT，但仓库 API 的许可证字段为 `NOASSERTION`；在使用或分发代码前仍需核验许可证全文。能完成复现和对照实验足以构成本科科研训练；创新性和可发表性尚无实验或文献证据，不能预先下结论。

## 2026-10-06｜TurtleBot3 仿真导航中的安全裕度—效率权衡

今天推荐 [ROBOTIS-GIT/turtlebot3](https://github.com/ROBOTIS-GIT/turtlebot3) 的 ROS 2 导航包，项目题目可以定为“窄通道中代价地图膨胀参数对移动机器人导航安全性与效率的影响”。它面向的不是“重新实现 Nav2”，而是把官方 TurtleBot3 Burger 的已有导航管线当作可控实验平台：在相同地图与任务下，改变障碍物周围的安全代价如何改变机器人是否能通过窄通道、离障碍物多近、走多远和耗时多久。这个问题和自动化中的感知—定位—规划—控制闭环直接相连，也能在没有实体车的前提下完成第一阶段。

代码入口是 [`turtlebot3_navigation2/launch/navigation2.launch.py`](https://github.com/ROBOTIS-GIT/turtlebot3/blob/main/turtlebot3_navigation2/launch/navigation2.launch.py) 与 [`turtlebot3_navigation2/param/burger.yaml`](https://github.com/ROBOTIS-GIT/turtlebot3/blob/main/turtlebot3_navigation2/param/burger.yaml)。前者把地图、仿真时钟和模型对应参数传给 Nav2；后者已经配置了 AMCL、局部与全局代价地图、Navfn 全局规划器和 DWB 局部规划器。Burger 的原始配置把局部/全局代价地图的膨胀半径设为 $0.5\,\mathrm{m}$、代价衰减系数设为 $5.0$，并固定了 DWB 的速度、加速度、采样数和评价项。这些现成值正好提供了明确的基线，而不是凭空挑一个算法名称。

实践范围应刻意缩小为只改 `inflation_radius` 与 `cost_scaling_factor` 两组参数；不更换全局规划器、不改机器人运动学、不接入学习算法。先用官方配套的 [ROBOTIS-GIT/turtlebot3_simulations](https://github.com/ROBOTIS-GIT/turtlebot3_simulations) 在 Gazebo 中生成两个测试环境：一个宽通道与一个仅略宽于机器人安全边界的窄通道。每个环境放置三组固定起点—终点；参数调优只在另一张训练地图进行，最终两张测试地图不得据结果反复回调参数。这样，研究对象始终是“安全裕度参数的取值”，而不是被地图、起终点或速度上限悄悄混入的综合差异。

可检验的问题是：在固定 TurtleBot3 Burger 模型、地图分辨率、起终点、Nav2 版本、速度与 DWB 配置时，膨胀半径和代价衰减系数的组合，能否在不显著降低到达率的前提下提高最小障碍物间距？先把官方默认的 $0.5\,\mathrm{m}$ 与 $5.0$ 作为基线，再预先写死例如半径 $0.30$、$0.50$、$0.70\,\mathrm{m}$ 及衰减系数 $3$、$5$、$8$ 的候选网格。实验前应明确“可接受安全距离”和超时阈值；若地图分辨率或机器人足迹变化，就重新声明该阈值，不能沿用旧结论。

公平比较时，每一组只允许改这两个 YAML 字段，并固定仓库提交版本、ROS 发行版、仿真世界、地图、激光与里程计噪声设定、起终点、最大线速度、规划超时和重复次数。报告到达率、碰撞或恢复次数、最小障碍物间距、路径长度、到达时间、平均与峰值角速度；将规划失败、超时、碰撞和到达目标分别计数，不能把失败样本从均值里悄悄删除。若使用随机噪声，应保存随机种子并对每种组合重复运行；若尚未注入噪声，则如实报告这是确定性仿真而不是鲁棒性结论。

四到六周的路线是：第一周选定与本机 ROS 2 发行版一致的分支，跑通原始地图与导航启动文件；第二周写最小数据记录脚本，确认每项指标的定义和失败分类；第三周完成训练地图上的参数网格；第四周冻结参数并在两张未参与调参的测试地图上比较；第五周加入固定强度的传感器或初始位姿扰动；第六周整理图表、配置文件和一页结果解释。先修知识是 Linux 基本操作、Python 或 C++ 的数据处理、ROS 2 的 topic/launch/参数文件、二维坐标与基础概率统计。普通电脑可先完成 Gazebo 仿真；实体 TurtleBot3、激光雷达和 OpenCR 只属于后续迁移验证，不是本任务的前置条件。

验收应交付一个可重放的 ROS 2 工作空间、未修改的官方参数副本和所有参数变体、固定地图与起终点清单、每次运行的 CSV 或 rosbag、指标汇总表、轨迹/代价地图截图，以及说明何种场景下安全性和效率发生冲突的短报告。仓库已有能力只是导航启动与参数模板；“某一参数更安全”是待检验假设；本次尚未在本机安装、编译或运行任何仿真，因此没有性能结果可报告，也不预先承诺创新性或发表价值。

核验状态：2026-10-06 已通过 GitHub 官方 API 读取主仓库 README、上述启动文件、Burger 参数文件、许可证与仓库元数据。`turtlebot3` 未归档，许可证字段为 Apache-2.0；README 明示 `humble`、`jazzy` 与 `main`（rolling）为活跃分支。上述两个关键文件最近一次提交分别为 2025-03-21 和 2025-03-25，主仓库元数据最近更新于 2026-10-05。配套仿真仓库也已核验为未归档、Apache-2.0；这些只说明源码与配置可获得，不构成运行成功或实验有效的证明。没有嵌入项目图片：主仓库 README 中可核验的图片是产品标志，不能展示导航效果，故不把装饰图当作实验材料。

## 2026-10-07｜simple-pid 温控实验：积分限幅与回算抗饱和

今天推荐 [m-lundberg/simple-pid](https://github.com/m-lundberg/simple-pid)，实践题目为“加热功率受限时，积分处理方式如何影响温度跟踪与恢复”。加热器达到最大功率后，继续增大控制指令已经不能增加加热能力；如果积分项仍持续累积，温度接近目标时可能继续大功率加热，或在目标温度降低后迟迟不能退出饱和。这个项目能把误差、反馈、积分、执行器约束和动态响应连接起来，适合自动化专业大二、三学生用普通电脑开展一个范围明确的控制实验。

具体代码入口是 [`simple_pid/pid.py`](https://github.com/m-lundberg/simple-pid/blob/6e6f4b000cdf7830635674cb89a6e823f5025784/simple_pid/pid.py) 中的 `PID.__call__()`，以及 [`examples/water_boiler/water_boiler.py`](https://github.com/m-lundberg/simple-pid/blob/6e6f4b000cdf7830635674cb89a6e823f5025784/examples/water_boiler/water_boiler.py) 中的 `WaterBoiler.update()` 和闭环循环。前者计算比例、积分、微分项，并对积分项和最终输出分别限幅；后者演示温度测量如何送入控制器，再由功率驱动被控对象。可以用 `PID(Kp, Ki, 0, sample_time=None, output_limits=(0, 1))` 构造 PI 基线，每步调用 `pid(T_meas, dt=0.1)`，并用 `pid.components` 记录各项贡献。这些接口已与[作者 API 文档](https://simple-pid.readthedocs.io/en/latest/reference.html)核对；代码中的增益和测量量仍须由实验程序定义。

仓库自带的水锅炉示例采用简化的功率加热和固定散热项，并按真实时钟运行约十秒。它适合读懂闭环结构。为了得到可重复的对照，本项目在自己的实验目录中保留上游源码副本，另写固定仿真步长的对象与记录程序，第一阶段统一令微分增益为零，只研究积分处理方式。仓库已经具备积分数值限幅；把它作为正式基线，回算抗饱和作为需要自行实现并检验的另一种已有方法。

建议使用如下自建的一阶温度对象。令 $T$ 为真实温度，$T_a$ 为环境温度，$u\in[0,1]$ 为归一化加热功率，$d$ 为与温度同量纲的等效热负荷项，$y$ 为送给控制器的测量值：

$$
\tau\frac{dT}{dt}=-(T-T_a)+Ku+d,
\qquad y=T+\varepsilon.
$$

用固定步长的前向欧拉法更新：

$$
T_{k+1}=T_k+\frac{\Delta t}{\tau}
\left[-(T_k-T_a)+Ku_k+d_k\right].
$$

拟定 $T_a=20\,^{\circ}\mathrm C$、$T_0=20\,^{\circ}\mathrm C$、$\Delta t=0.1\,\mathrm s$，每次运行六百秒。名义对象为 $\tau=60\,\mathrm s$、$K=80\,^{\circ}\mathrm C$，评价对象取 $\tau\in\{30,60,90\}\,\mathrm s$ 与 $K\in\{60,80,100\}\,^{\circ}\mathrm C$ 的组合。这里 $K$ 表示满功率时相对于环境温度的稳态温升；这些数值是拟定的仿真参数，未由真实设备辨识，也不是仓库提供的水锅炉参数。

比较三类控制器：第一类仅将最终功率截断到 $[0,1]$，积分项不设限，用来观察积分累积的作用；第二类保留 simple-pid 的积分限幅与输出限幅；第三类用回算修正积分项，同时保持相同的最终功率限制。若实现第一类，应在独立实验副本中只移除积分项的限幅，保留最终输出限幅；直接取消 `output_limits` 会同时改变执行器约束，使比较失去解释力。

回算版本可以明确规定如下离散计算顺序。先令 $e_k=r_k-y_k$，其中 $r_k$ 为目标温度，再计算

$$
\begin{aligned}
\widetilde I_k&=I_{k-1}+K_i e_k\Delta t,\\
v_k&=K_p e_k+\widetilde I_k,\\
u_k&=\operatorname{clip}(v_k,0,1),\\
I_k&=\widetilde I_k+\frac{\Delta t}{T_t}(u_k-v_k).
\end{aligned}
$$

其中 $v_k$ 是限幅前的功率指令，$T_t>0$ 是回算时间常数，修正后的 $I_k$ 进入下一步。功率受到上限约束时，$u_k-v_k$ 为负，反馈项会抵消一部分积分累积。该版本不再同时套用库内的积分数值限幅，否则会混入两种机制。回算使用饱和前后控制量的差来修正积分器，是已有抗饱和思路，原理可参见 [MathWorks 官方说明](https://www.mathworks.com/help/simulink/slref/anti-windup-control-using-a-pid-controller.html)。上式是本项目选定的离散实现方案，尚未执行验证。

可检验的研究问题是：在相同 PI 增益、采样周期和功率限制下，回算抗饱和相对于仓库积分限幅，能否缩短目标温度下降或冷负荷加入后的恢复时间，并降低积分绝对误差？待检验的假设是回算能够减轻饱和后的积分残留，但不同 $T_t$ 可能改变升温速度与恢复效果；结果也可能表明库内积分限幅已足够。结论应明确对应的参数和工况。

公平对照需固定比例项按误差计算、$K_d=0$、初始积分为零，并让各方法共享同一组 $K_p,K_i$。可从 $K_p=0.05\,({}^{\circ}\mathrm C)^{-1}$、$K_i=0.001\,({}^{\circ}\mathrm C\cdot\mathrm s)^{-1}$ 开始，在名义对象上检查响应后确定共同增益，再冻结它们。其余八组对象不参与增益选择。回算时间常数预先取 $T_t\in\{30,60,120\}\,\mathrm s$，三个候选都报告；不根据测试结果挑选一个最好值来代表全部回算控制器。整个实验只改变积分处理方式，共享模型更新顺序、步长、初始状态、运行长度、目标序列和扰动。

测试采用两个单独工况。目标反转工况在开始时把目标设为 $60\,^{\circ}\mathrm C$，三百秒时降到 $30\,^{\circ}\mathrm C$，全程 $d=0$；负荷工况将目标保持在 $60\,^{\circ}\mathrm C$，三百秒时令 $d$ 从零变为 $-10\,^{\circ}\mathrm C$ 并保持。先由 $T_\infty=T_a+Ku+d$ 检查目标是否可达：本组参数下，两个目标均在对应功率范围内。运行前还应确认升温段确实触及功率上限，否则该工况难以揭示抗饱和差异。先完成无噪声比较，再加入标准差 $0.5\,^{\circ}\mathrm C$ 的零均值高斯测量噪声，使用二十个固定种子；同一对象、工况和种子的不同控制器使用同一条噪声序列。

指标用真实温度计算，带噪测量值只用于控制。积分绝对误差定义为

$$
\mathrm{IAE}=\Delta t\sum_k|r_k-T_k|.
$$

分别报告变化前、变化后的 IAE，上升段超调、下降段欠调，以及目标或负荷变化后首次进入 $\pm1\,^{\circ}\mathrm C$ 误差带并连续保持六十秒所需的时间。六百秒内没有满足条件的运行记为“未恢复”，同时报告发生比例。还要画出积分项、限幅前指令与实际功率，统计处于功率上下限的时间比例，才能判断差异是否来自饱和处理。$\Delta t\sum_k u_k$ 只称为归一化加热投入；没有额定功率就不能写成实际能耗。每个对象和工况单独汇总，同一种子进行配对比较，采样时刻不能当作独立实验样本。

先修知识包括 Python 函数与类、循环和数据保存，比例积分反馈的含义，一阶微分方程及欧拉离散，以及均值、标准差和随机种子的作用。软件方面需要 Python、simple-pid，以及示例声明的 NumPy、Matplotlib；[项目配置](https://github.com/m-lundberg/simple-pid/blob/6e6f4b000cdf7830635674cb89a6e823f5025784/pyproject.toml)声明 Python 版本至少为 3.6，复现时还应记录实际使用的解释器与依赖版本。第一阶段普通 Windows 或 Linux 电脑即可，不要求购买加热器、开发板或传感器。

## 2026-10-11｜CVXPY：受容量约束的多执行器分配

推荐 [cvxpy/cvxpy](https://github.com/cvxpy/cvxpy)。它提供凸优化问题的 Python 建模、规范化与求解器接口。把实践缩小为三个执行器共同承担总需求的静态分配问题，可以把线性代数、二次型与自动化系统中的控制分配、饱和约束联系起来。这里的执行器是仿真抽象，可理解为并联泵或协同出力单元，不假定真实设备的效率曲线。

固定提交 `0049909353bb649fcb89f427a3dd2eb9702d6d00` 的入口是 [README](https://github.com/cvxpy/cvxpy/blob/0049909353bb649fcb89f427a3dd2eb9702d6d00/README.md)、[二次规划示例](https://github.com/cvxpy/cvxpy/blob/0049909353bb649fcb89f427a3dd2eb9702d6d00/doc/source/examples/basic/quadratic_program.rst) 和 [Problem.solve 实现](https://github.com/cvxpy/cvxpy/blob/0049909353bb649fcb89f427a3dd2eb9702d6d00/cvxpy/problems/problem.py)。先从 `Variable`、`Minimize`、约束列表到 `Problem.solve()` 走通一次，再读 `status`、`value` 与 `solver_stats`；建模层将问题交给数值求解器完成求解。本次分配模型是学生新增实例。

先修知识为 Python、矩阵和向量、二次型、拉格朗日乘子与基本凸性。普通电脑即可。当前核验提交的 README 要求 Python 至少 3.11，并列有 NumPy、SciPy 及求解器依赖；安装时记录实际版本和 `installed_solvers()` 返回值。第一阶段选择 OSQP 求解这一凸二次问题，不需要硬件或商业求解器。

可检验问题是：给定相同总需求和相同容量，按二次成本优化的分配，相比等份后容量重分配的策略能降低多少归一化成本，优势怎样随成本不均匀程度与饱和位置变化？基础模型为

$$
\min_{u\in\mathbb{R}^3}\sum_{i=1}^3\alpha_i u_i^2,\qquad \sum_{i=1}^3u_i=d,\quad0\leq u_i\leq c_i.
$$

拟取容量 $c=(0.6,0.8,1.0)$，成本权重分别为 $(1,1,1)$、$(1,2,4)$、$(4,2,1)$，需求从零到总容量之间取 49 个等距点。所有成本均为归一化代理量；没有实测功率曲线时，不能把它们写成节省了多少电能。

公平基线从等份 $d/3$ 开始：达到容量的执行器固定在上限，剩余需求继续在其余执行器间等分，重复直到分配完成。这保证基线也满足需求和容量，避免拿“分别裁剪后需求不足”的错误基线制造优势。每个成本组和需求点同时计算基线及优化解，不在测试点上改权重或约束。

本模型还有独立参考解：由最优性条件得到 $u_i=\min\{c_i,\lambda/(2\alpha_i)\}$，选择 $\lambda\geq0$ 使总和等于 $d$，可用二分法或枚举饱和集合实现。比较 CVXPY 解与这份独立实现，检查成本、需求残差及容量违反，而非只相信求解状态。故“优化不会比任何可行基线更差”是精确模型最优解的数学性质；数值实验要核实误差大小，并量化这种特定基线的差距。

指标为需求残差、最大约束违反、归一化成本、与独立参考解的差值、求解失败数量和端到端耗时。成本差使用绝对差；相对改善在基线成本为零时留空。测试需求超过总容量的一组额外案例时，应如实报告不可行，不能把需求悄悄裁剪后冒充原题的解。

效率扩展单独比较每次重建问题与使用 `Parameter` 复用问题；按 [官方性能文档](https://www.cvxpy.org/tutorial/performance/index.html) 检查 `is_dpp()`，共享求解器、精度与输入顺序。首次构建和首次求解单列，后续请求耗时另列；暖启动设置一致，端到端计时包括建模与规范化。基础成本实验和效率实验回答不同问题，各自保持自己的公平条件。

## 2026-10-12｜Bullet/PyBullet：单关节显式 PD 与 Stable PD 的采样周期对照

推荐 [bulletphysics/bullet3](https://github.com/bulletphysics/bullet3)。这是 Bullet Physics SDK 的官方仓库，提供刚体动力学、碰撞检测及 PyBullet Python 接口，实际用于机器人等系统的物理仿真。已有学习笔记讨论了编码器角速度与电机 PWM，本项目进一步把角度、速度和力矩连接成反馈回路。适合自动化专业本科二、三年级先完成一个电脑上的关节控制实验，再考虑硬件；不要求购买机械臂或学习强化学习。

可检验研究问题是：**在相同连续 PD 增益、相同力矩上限与相同物理积分精度下，增大控制采样周期时，Stable PD 相比显式 PD 能否扩大满足误差与恢复时间要求的周期范围，饱和是否改变这种差异？** 名称中的 Stable 不构成对任意步长、增益或饱和条件的稳定性保证，效果必须逐工况检验。

缩小范围为固定基座、一个刚体和一个连续旋转关节，总关节数为 1，索引列表为 `[0]`，避免混入固定关节或多自由度接口。关闭重力、不加接触，模型关节阻尼设为零；先以零输入匀速试验检查是否仍有隐含阻尼，再核对运行时质量矩阵中的标量惯量 $I$。这类结构可近似成 $I\ddot q=\tau$。模型文件、惯量检查和零输入试验都尚未执行，不能把它当作真实电机的完整模型。

零目标速度、角度误差 $e=q_d-q$ 时，显式 PD 的未限幅力矩是 $\tau_E=k_pe-k_d\dot q$。将已读取的 Stable PD 源码化简到单关节、无重力的情形，未限幅力矩为

$$
\tau_S=\frac{k_pe-(k_d+k_ph)\dot q}{1+k_dh/I},
$$

其中 $h$ 是传给控制器的采样周期。两者最后都采用同一个 $[-\tau_{\max},\tau_{\max}]$ 限幅。该式已按源码中的中间加速度方程进行代数核对；这只是公式核验，尚不是仿真性能结果。对复杂机构，应继续用源码的质量矩阵与逆动力学计算，不能直接套这个标量式。

拟定基础实验初态为 $q=0,\dot q=0$，目标阶跃为 $q_d=0.3$ rad，运行 6 秒。选择自然频率 $\omega_n\in\{10,20,40\}$ rad/s、阻尼比 $\zeta=1$，共同设置 $k_p=I\omega_n^2$、$k_d=2\zeta I\omega_n$，并比较 $\tau_{\max}/I\in\{50,200\}$ rad/s²。每个工况的两控制器使用完全相同的增益和上限，不为其中一方单独调参。

公平对照取控制周期 $h\in\{0.001,0.002,0.005,0.01,0.02,0.05\}$ 秒，共 36 个条件、每条件一对控制器。物理积分步长固定为 0.0005 秒，控制器只在对应采样时刻计算力矩，期间保持输出；按原示例的方法关闭默认关节电机，避免内置控制器暗中参与。原官方演示一起调整物理步长，本实践把物理步长与控制周期分开。Stable PD 的 `timeStep` 传入控制周期是本实验采用的应用选择，须在第一阶段确认两接口和保持策略一致。

另建独立的理想转子参考：在每个力矩保持区间用 $q_{k+1}=q_k+h\dot q_k+h^2\tau_k/(2I)$、$\dot q_{k+1}=\dot q_k+h\tau_k/I$ 精确推进，与 PyBullet 结果比较。这可以检查是否由仿真积分或模型设置引入差异；它没有覆盖真实摩擦、接触、传感器噪声和执行延迟。若加入这些因素，应另设扩展实验，保留原来的基础对照。

指标包括角度 IAE、最大绝对误差、超调量、进入并在余下时间持续满足 $|e|\leq0.01$ rad 和 $|\dot q|\leq0.05$ rad/s 的恢复时间、力矩 RMS、限幅时间比例，以及实际控制调用次数。未在 6 秒内恢复的条件报告未恢复；非有限值或 $|q|>3$ rad 时终止并计为失效。逐条件保存两方案的配对指标，不丢弃失效样本。基础实验是确定性的，不把重复同一轨迹作为独立统计样本，也不把力矩平方指标写成实际电耗。

拟生成三类模拟信号：基线波形、二次谐波增强、周期性冲击。每段运行采样率为 2048Hz、时长 10 秒，切成十个互不重叠的一秒窗。基础信号由基频正弦、二次谐波和高斯噪声组成；每段运行独立抽取基频 15—25Hz、幅值 0.8—1.2、相位及噪声标准差 0.05—0.15，段内保持这些条件。基线类二次谐波相对幅值取 0.1—0.3，增强类取 0.25—0.5；冲击类在基线信号上叠加频率为五倍基频、宽度 3ms、相对幅值 0.3—0.8 的窄高斯脉冲列。数值为教学模型，类别有意保留部分重叠，脉冲列不宣称是某款轴承的物理故障模型。

固定六个窗口特征：RMS、峰峰值、峰值因子、中心化峰度、主频估计和二次谐波/基频能量比。频域特征统一先去均值并加 Hann 窗，主频从波形频谱估计，谐波能量用该估计频率附近的共同频带计算，频带宽度在实验前冻结。生成器真实参数仅留作核验，不直接传给分类器；运行编号、文件名和类别标签也不能当输入特征。零 RMS 或零方差情况需要明确处理和计数。

每类拟生成 40 段独立运行：30 段构成开发集、10 段构成共同独立测试集，总计 120 段、1200 个窗口。独立测试集在划分协议确定前封存，其运行编号与所有开发数据隔离。协议 A 在开发窗口中按类别分层做 80%/20% 随机切分；协议 B 在每类 30 段运行内用 `GroupShuffleSplit(test_size=0.2)` 保留 6 段验证、24 段训练，再合并三类。这使两协议各有 720 个训练窗、180 个内部验证窗，且类别数一致；共同测试集为 300 窗。

公平对照使用相同生成数据、特征及随机森林参数：100 棵树、最大深度 6、叶节点至少 3 个样本、同一随机种子和单线程。两模型分别在自己的训练部分拟合，既计算内部验证指标，也在同一个封存测试集上评估。运行编号只传给划分器。分组协议必须检查训练与验证运行编号交集为空，两协议都要检查与测试运行编号的交集为空；窗口协议的共享运行数量作为诊断量报告。任何需要拟合的预处理仅在训练部分完成，不使用测试数据挑特征、调参数或反复选择最好划分。

主指标为内部与独立测试的 macro-F1、各类召回率、混淆矩阵，以及验证—测试差距 $g=F1_{val}-F1_{test}$ 和 $|g|$。同时保存每段独立测试运行的错误率及两协议的有效训练运行数量。用 20 个独立数据生成种子重复完整实验，同一份数据供两协议配对使用，以数据集重复和采集运行为统计单位，不能把段内十个窗口当十次独立重复。分组切分同时改变训练运行覆盖数量，因此本设计比较整体评估协议，不把全部差异归因于单一泄漏因素。如果两协议差距都小，也应如实报告这个生成条件下未观察到明显乐观偏差。

五周路线为：第一周读官方划分示例，掌握类别标签与运行组的区别；第二周生成信号、保存分组元数据和六个特征，检查时间窗与频谱；第三周实现两套固定划分并加入编号隔离检查；第四周冻结模型和协议，完成 20 个配对数据集；第五周整理验证—测试差距、混淆矩阵和逐运行错误，解释结论的适用条件。四周可先做少量数据集调试，正式报告说明重复数；六周可以在本方案完成后增加有真实采集编号与可靠标签的公开数据，先重新核验来源和分组含义。

验收成果包括源码参考提交及许可证、环境版本、信号生成器、特征提取脚本、数据种子与运行编号、两种划分索引、隔离检查、模型配置、原始特征 CSV、独立测试预测、配对指标表和短报告。报告应能复现每个分数来自哪些运行，明确区分合成波形分类、真实设备诊断和评估方法结论，不承诺创新或发表。

## 2026-10-14｜AprilTag：标签像素尺度、位姿误差与检测速度的可复现实验

推荐 [AprilRobotics/apriltag](https://github.com/AprilRobotics/apriltag)。这是一个用于机器人研究的视觉标记系统，仓库提供 AprilTag 3 的检测、标签族和位姿估计。它适合自动化专业本科二、三年级把相机坐标系、标定、视觉定位和机器人末端或移动平台对位联系起来。项目先在固定相机与单张标签的受控条件下完成，不把演示结果外推成通用的机器人定位精度。

仓库已有能力包括标签检测、多个标签族和根据检测角点估计六自由度位姿。固定提交 `b7c0ebe9aa20f82ec7a828579004f9e706bfecd9` 的 [README](https://github.com/AprilRobotics/apriltag/blob/b7c0ebe9aa20f82ec7a828579004f9e706bfecd9/README.md) 推荐 `tagStandard41h12` 用于多数应用，并说明标签尺寸应在检测角点之间、即黑白边界处测量。检测入口可从 [example/apriltag_demo.c](https://github.com/AprilRobotics/apriltag/blob/b7c0ebe9aa20f82ec7a828579004f9e706bfecd9/example/apriltag_demo.c) 的标签族创建、检测器设置和 `apriltag_detector_detect()` 开始阅读。位姿入口是 [apriltag_pose.c](https://github.com/AprilRobotics/apriltag/blob/b7c0ebe9aa20f82ec7a828579004f9e706bfecd9/apriltag_pose.c) 的 `estimate_tag_pose()`：它使用标签尺寸、$f_x,f_y,c_x,c_y$ 和检测结果，返回旋转矩阵、平移向量及候选中较低的对象空间误差。官方源码也说明 `quad_decimate` 增大可提高速度而会损失远距离检测能力。

代码入口与先修条件：先读 README 的标签尺寸和坐标系说明，再用 `example/apriltag_demo.c` 跑通检测，最后进入 `apriltag_pose.c` 核对位姿估计的输入与误差含义。需要 C 或 C++ 基础、线性代数中的旋转矩阵与坐标变换、相机内参的含义，以及均值、中位数和标准差。硬件条件是可固定的相机、打印标签、直尺、量角器和支架；软件条件是 Linux 或可用的等价环境、CMake 和用于数据整理的 Python 或表格工具。

![README 中标出的标签尺寸测量边界](https://raw.githubusercontent.com/AprilRobotics/apriltag/b7c0ebe9aa20f82ec7a828579004f9e706bfecd9/tag_size_48h12.png)

图片来自已核验的 README 原始文件，说明 `tagsize` 的测量边界，与本实验的物理尺寸设置直接相关；没有下载图片。仓库 README 说明其官方支持 Linux，Windows 上有人安装成功但不构成支持承诺。普通电脑、一个可固定的 USB 摄像头或手机相机、打印标签、直尺、量角器和稳定支架足够。若使用 Windows，应先确认 Linux、WSL 或可用相机采集路径；本机尚未验证构建或相机访问。

项目的缩小范围是一张 `tagStandard41h12` 标签，检测边界间实测边长为 100mm，固定相机分辨率和焦距。相机先用独立标定板求内参，保存 $f_x,f_y,c_x,c_y$ 与标定重投影误差；标签放在镜头光轴附近，标签中心高度与镜头中心尽量对齐。用直尺记录镜头主平面到标签平面的轴向距离，用量角器记录标签平面绕竖直轴的偏转角。这里的物理定位方法是待执行的实验协议，直尺和量角器带来的误差要如实报告。

可检验研究问题是：**在固定相机标定、标签族、光照和原始视频条件下，`quad_decimate` 从 1 提高到 2、3 时，检测速度的变化是否伴随远距离或倾斜标签的检测率下降、轴向距离误差上升与位姿抖动增加？** README 给出速度与检测距离的调参方向，本项目把它变成给定设备上的可测假设；没有实验数据前，不预设哪一项的变化量。

数据采集设置为轴向距离 $d\in\{0.3,0.6,0.9,1.2\}$ m、偏转角 $\theta\in\{0^\circ,30^\circ\}$，共 8 个物理条件。每个条件独立重新放置标签并录制 10 段三秒视频，共 80 段。相机分辨率、帧率、焦距、曝光、白平衡、标签尺寸、环境光、标签族、允许的汉明距离、`quad_sigma`、`decode_sharpening`、`refine_edges` 和线程数在实验前固定；线程数设为 1，避免并行调度把检测器参数比较混入硬件资源差异。

公平对照只改变 $q=\operatorname{quad\_decimate}\in\{1,2,3\}$。同一段已记录的原始视频依次用三个 $q$ 值处理，因此每帧图像、相机标定和实际标签姿态完全配对。不能为了较大 $q$ 另录一段更亮、更近或更稳定的视频。若某个配置没有检测到标签，将该帧记为未检测，不以插值姿态填补。各条件的采集顺序随机化，避免光照或相机温度随时间单向变化后恰好对应某个距离。

每段视频汇总为一个独立重复，而不是把三秒内连续帧视为许多独立实验。主要指标是每段检测率、成功检测帧的中位数轴向误差 $|\hat t_z-d|$、基于旋转矩阵与量角器读数的偏转角误差、固定目标下平移和角度估计的标准差，以及每帧检测加位姿估计的中位耗时。`estimate_tag_pose()` 返回的对象空间误差也记录为算法内部拟合诊断，但不把它等同于真实物理距离误差。每个物理条件比较同一视频在三种 $q$ 下的配对差值，先报告 10 段的分布和失效段数，再讨论总体趋势。

位姿的真实距离只在标签中心靠近光轴、测距起点明确时才有可解释性。若标签偏移较大，应额外记录横向位移，或将指标改为完整三维平移误差；不能继续把 $t_z$ 单独称为相机到标签的直线距离。相机内参、标签尺寸和距离测量都可能产生系统误差，因此同一标签的重复录像可评估重复性，不能单独证明绝对精度。

## 2026-10-15｜Open3D：初始位姿偏差与部分重叠下的 ICP 配准成功域

推荐 [isl-org/Open3D](https://github.com/isl-org/Open3D)，把实践缩小为“在已知真值的合成点云中，比较 point-to-point ICP 与 point-to-plane ICP 面对初始位姿偏差和部分重叠时的配准成功率”。Open3D 实际提供三维数据结构、处理算法、表面对齐和 Python/C++ 接口；点云配准对应自动化中的激光雷达或深度相机定位、工件抓取前对位和移动机器人建图。第一阶段只在电脑上构造有精确刚体变换真值的点云，不把结果外推为真实传感器、机械臂或车辆上的定位精度。

固定源码参考提交为 `b6c5e196384ad71e75b6e6f9c5da22d046221f1d`。已有能力的入口是 [README](https://github.com/isl-org/Open3D/blob/b6c5e196384ad71e75b6e6f9c5da22d046221f1d/README.md)、[ICP Python 示例](https://github.com/isl-org/Open3D/blob/b6c5e196384ad71e75b6e6f9c5da22d046221f1d/examples/python/pipelines/icp_registration.py) 和 [Registration.cpp](https://github.com/isl-org/Open3D/blob/b6c5e196384ad71e75b6e6f9c5da22d046221f1d/cpp/open3d/pipelines/registration/Registration.cpp)。示例使用 `o3d.data.DemoICPPointClouds()` 读取两份点云，再用 `registration_icp()` 分别配合 `TransformationEstimationPointToPoint()` 与 `TransformationEstimationPointToPlane()` 运行 ICP；它还调用 `evaluate_registration()` 查看初始对齐。底层实现为目标点云建立 KD 树，在 `max_correspondence_distance` 内收集最近邻对应，迭代更新变换，并返回 `fitness` 与 `inlier_rmse`。当前官方文档接口也明确 point-to-plane ICP 需要法向量；本实践会显式为两份点云估计法向量，不能把示例中已带法向量的数据当作普遍前提。

先修知识包括 Python、NumPy 数组、三维坐标系、刚体变换矩阵、欧氏距离、均值和中位数。软件需要 Python、Open3D、NumPy、Matplotlib 和 CSV/Parquet 数据保存工具。README 已列出 Windows 10+、Ubuntu 20.04+ 与 macOS 上的 Python 3.10—3.14 预编译包；普通电脑的 CPU 足以完成小规模实验，不要求 GPU、相机、激光雷达或机械臂。GPU 加速是仓库已有能力，但不是本项目的对照变量。

可检验研究问题是：**在相同点云、初始变换、体素下采样、最大对应距离和停止准则下，point-to-plane ICP 是否会比 point-to-point ICP 在较大的初始偏航误差或 70% 可见重叠条件下取得更高的真值配准成功率？** “point-to-plane 的收敛域可能更大”只是待检验假设；它依赖表面几何、法向量质量、噪声、部分重叠和初始猜测，不能由代码示例直接推出。

实验先从 `DemoICPPointClouds` 的第一份点云取一个固定、下采样后的母点云 $P$，用预先保存的刚体变换 $T^\ast$ 生成目标云，再按固定随机种子施加坐标高斯噪声和裁剪，以制造已知真值的完整重叠或约 70% 重叠样本。$\hat T$ 始终与 $T^\ast$ 比较，而不是以 ICP 自身的 `fitness` 或 `inlier_rmse` 代替真值误差。准备阶段只使用一份独立的调试点云冻结体素尺度 $v$、法向量邻域、最大对应距离 $3v$、相对收敛阈值和最大迭代次数；正式网格不再为任一方法单独调参。

正式条件设置为初始偏航误差 $\delta\theta\in\{0^\circ,5^\circ,10^\circ,15^\circ,20^\circ\}$、沿固定横向轴的初始平移误差 $\delta t\in\{0,2v,4v,6v\}$、重叠比例 $\{100\%,70\%\}$、噪声标准差 $\{0,0.25v\}$，每个条件取 10 个共同随机种子。每个种子先生成同一对 source—target 点云和同一初始变换，再由两种估计器配对处理。point-to-point 与 point-to-plane 使用相同的点坐标、下采样结果、法向量估计、对应距离、迭代上限和 CPU 环境；前者不使用法向量求解，但保留共同预处理，避免把不同输入点集混入算法差异。报告“仅 ICP 求解时间”时不计共同法向量估计；若报告端到端时间，需单列预处理与求解时间，不能把后者误写成纯估计器速度。

主要指标是平移误差 $e_t=\lVert\hat t-t^\ast\rVert_2$、旋转角误差 $e_R=\arccos\left((\operatorname{tr}(\hat R R^{\ast T})-1)/2\right)$、成功率、`fitness`、`inlier_rmse`、失败类型和求解时间。可将 $e_t\leq v$ 且 $e_R\leq2^\circ$ 预先定义为一次成功；阈值随配置写入报告，不得在查看结果后修改。每个条件报告 10 个配对种子的成功数、误差中位数与四分位距，保留无对应点、收敛到错误局部解和数值异常的全部失败样本。重复运行同一确定性输入只用于测量计时抖动，并取中位数，不能当成新的几何实验重复。

可检验研究问题是：**对 Panda ETS 的可达目标位姿，目标源关节配置的雅可比矩阵较病态、且初始猜测偏离该配置时，Chan、Sugihara、Wampler 三种 LM 阻尼策略在相同迭代预算内的成功率、实际末端误差和迭代次数是否不同？** `IK_LM` 源码说明阻尼矩阵的选择影响 LM 表现，并提示初值应对应非奇异姿态；这支持提出问题，不能预先推出哪一种方法更好。

每次求解记录 `IKSolution` 的 `success`、`iterations`、`searches`、`residual` 和 `reason`，但只在 `success` 为真时使用返回关节角。另用正运动学独立计算末端位置误差 $\lVert\hat p-p_{\mathrm{ep}}\rVert_2$ 和旋转角误差；事先定义位置不超过 $1$ mm、旋转不超过 $1^\circ$ 且 `success` 为真的条件为成功。`residual` 是加权角轴误差的二次型，源码明确它不等同于毫米或角度的直接上界，因此不能单独作为精度结论。还报告失败原因、迭代次数、搜索次数和预热后求解时间中位数；同一输入的重复计时只刻画运行时间抖动，不能当作独立运动学样本。

## 2026-10-17｜CMSIS-DSP：FIR 低通中 Q15 量化误差与饱和边界

实验固定原示例的 $1$ kHz 与 $15$ kHz 双正弦任务，生成一秒长、相位由固定种子给出的 float32 基准序列，并先缩放使其绝对值不超过 $1$。在增益 $g\in\{0.2,0.5,0.8,0.95\}$ 下，对同一输入建立三条链路：A 为原始 float32 系数和 float32 输入的参考输出；B 将系数量化为 Q15 后再反量化为 float32，仅测系数量化；C 将系数和输入都转为 Q15，调用 `arm_fir_q15` 后反量化输出，测完整定点链路。Q15 转换采用四舍五入后限制到 $[-32768,32767]$，缩放因子固定为 $2^{15}$；每条链路从全零状态重新开始，防止前一条件的 FIR 历史样本泄漏到下一条件。

## 2026-10-18｜Gymnasium-Robotics：FetchPush 中后方对准策略对推块成功率的影响

推荐 [Farama-Foundation/Gymnasium-Robotics](https://github.com/Farama-Foundation/Gymnasium-Robotics)，把项目限定为 FetchPush 中一个有明确状态、动作和成功条件的桌面推块任务：机械臂末端把台面上的方块推到目标位置。它适合把已有的 PID 速度环、采样时序和反馈误差概念迁到机械臂末端位置—物块位置—目标位置的闭环中。第一阶段不训练强化学习策略，也不接实体 Fetch 机械臂；只用仓库已有 MuJoCo 环境实现并比较两种确定性、基于状态反馈的推送策略。

固定源码参考默认分支提交 `b8da02a89191daf8f004e7f7510ff655f7a90100`。代码入口是 [FetchPush 环境](https://github.com/Farama-Foundation/Gymnasium-Robotics/blob/b8da02a89191daf8f004e7f7510ff655f7a90100/gymnasium_robotics/envs/fetch/push.py) 的 `MujocoFetchPushEnv`，以及 [通用 Fetch 环境](https://github.com/Farama-Foundation/Gymnasium-Robotics/blob/b8da02a89191daf8f004e7f7510ff655f7a90100/gymnasium_robotics/envs/fetch/fetch_env.py) 的 `_set_action()` 和 `generate_mujoco_observations()`。前者已定义方块、锁闭夹爪、`0.15` m 的物块/目标采样范围和 `0.05` m 成功距离阈值；后者把四维动作送入 MuJoCo，并返回夹爪位置、物块位置、相对位置和速度。任务实际以 `FetchPush-v4` 运行，动作是末端在笛卡尔坐标的 $x,y,z$ 位移加一个夹爪通道；环境内部按 $25$ Hz 控制频率推进，每步由 $20$ 个 $0.002$ s 仿真子步组成。README 说明目标导向观测同时含 `observation`、`achieved_goal` 与 `desired_goal`，因此可直接计算方块到目标的几何误差，不能把环境返回的奖励替代为唯一的研究指标。

该 GIF 是仓库树中 `docs/_static/videos/fetch/push.gif` 的原始资源，展示的正是本项目的 FetchPush 推块任务；它用于说明任务，不作为控制效果证据。

实践范围只比较两种手工状态反馈策略。基线策略 $C_{\mathrm{fixed}}$ 先把夹爪移动到方块沿“方块—目标”反方向、固定后方距离 $d_0$ 的对准点，再以固定高度沿方块到目标的方向推送；候选策略 $C_{\mathrm{adaptive}}$ 使用同样两阶段结构，但把后方距离设为 $d(\theta)=\operatorname{clip}(d_0+k\lvert\sin\theta\rvert,d_{\min},d_{\max})$，其中 $\theta$ 是重置时“夹爪到方块”向量和“方块到目标”向量的夹角。候选策略还只允许在固定的检查时刻重新回到后方对准点，不能为单个回合临时改动作上限或步数。这里已有的是环境、状态、动作与成功阈值；两种控制器、参数冻结和后续实验均为待实现内容。

可检验的研究问题是：**在相同 FetchPush-v4 任务、相同 $50$ 步时限、动作限幅和重置种子下，自适应后方对准距离是否比固定后方距离提高方块进入 $0.05$ m 成功半径的比例，并降低最终位置误差和推送过程中的横向偏离？** “自适应对准可能更稳”只是待验证假设。它可能在大夹角任务上减少侧撞，也可能因多次重新对准消耗步数；源码和 GIF 都不能预先给出结论。

公平对照应先用独立的 24 个校准种子选择 $d_0,k,d_{\min},d_{\max}$ 和检查间隔，并在正式实验前冻结。正式集至少使用 120 个共同重置种子，按初始夹角 $0^\circ$--$30^\circ$、$30^\circ$--$60^\circ$、$60^\circ$--$90^\circ$ 分层；每一对回合从同一 `reset(seed=s)` 状态开始，使用同一环境版本、稀疏奖励模式、动作裁剪、末端高度、最大步数和停止规则。两种策略只能改变后方对准距离规则，不得给候选策略额外观测、更多步数或单独挑选更容易的种子。若要加入动作噪声，应在两种策略的同一回合中使用同一随机扰动，并另列为扩展实验。

每个回合保存初始夹爪、物块、目标位置和动作序列，计算最终误差 $e_f=\lVert p_{\mathrm{object}}^{\mathrm{final}}-p_{\mathrm{goal}}\rVert_2$、成功率 $\mathbb{1}(e_f\leq0.05\,\mathrm{m})$、首次进入成功半径所需步数、累计动作范数，以及物块相对初始“物块—目标”直线的最大横向偏离。分夹角层报告共同种子上的成功数、$e_f$ 中位数与四分位距、步数中位数和失败轨迹数；同时保留方块被推离目标、时间耗尽和反复重对准三类失败日志。环境的 `dense` 奖励可附带记录，但它是负欧氏距离，不应与独立计算的成功率或几何误差混为一项指标。

## 2026-10-19｜robot_localization：协方差报告失配下双源 EKF 的定位可信度

## 2026-10-20｜acados：摆杆小车 NMPC 的预测时域—实时性权衡

可检验研究问题是：**在相同 $0.02$ s 控制周期、模型、输入界、代价权重和闭环步数下，预测时域从 $0.4$ s 增至 $0.8$、$1.6$ s，是否会提高摆杆小车从较大初始角度/角速度偏差回到零状态目标的成功率；这种变化是否值得第 $95$ 百分位求解时间和超周期求解比例的代价？** “更长时域一定更稳”只是待检验假设；更长的 NLP 也可能带来更慢求解、RTI 近似质量变化或没有可观增益，不能预先下结论。

## 2026-10-24｜Pymodbus：轮询周期与迟滞报警对模拟寄存器抖动的影响

推荐 [pymodbus-dev/pymodbus](https://github.com/pymodbus-dev/pymodbus)。它是 Python 的 Modbus 协议栈，包含客户端、服务端、模拟器和同步/异步接口，适合把工业自动化中的传感器寄存器、PLC/上位机轮询、报警状态机和通信异常处理放入一台电脑上的可重复实验。实践对象不是某个真实温控设备，而是一条有标签的合成测量轨迹写入 Modbus 保持寄存器；研究轮询多快才有意义，以及报警迟滞能否减少阈值附近的误触发。

固定源码参考 `dev` 默认分支提交 `add3009328da955b42c61daff2166b1307e89202`。代码入口为 [持续更新服务端](https://github.com/pymodbus-dev/pymodbus/blob/add3009328da955b42c61daff2166b1307e89202/examples/server_updating.py)、[同步 TCP 客户端](https://github.com/pymodbus-dev/pymodbus/blob/add3009328da955b42c61daff2166b1307e89202/examples/simple_sync_client.py)、[客户端保持寄存器读取接口](https://github.com/pymodbus-dev/pymodbus/blob/add3009328da955b42c61daff2166b1307e89202/pymodbus/client/mixin.py) 和 [数据存储上下文](https://github.com/pymodbus-dev/pymodbus/blob/add3009328da955b42c61daff2166b1307e89202/pymodbus/datastore/context.py)。服务端示例用 `ModbusTcpServer`、`SimDevice` 和 `SimData` 创建设备，并在独立异步任务中每两秒更新功能码 $3$、地址 `0x10` 的寄存器值；客户端示例用 `ModbusTcpClient.read_holding_registers()` 读取寄存器并检查 `isError()`。保持寄存器的 API 地址从零开始，这个细节应在实验日志中固定记录。已有的是协议通信、寄存器读写和模拟服务端；传感器轨迹、报警逻辑和研究指标均待新增。

实践范围固定为回环地址上的一个 TCP 服务端、一个十六位保持寄存器和一个轮询客户端。将合成标量信号以固定比例编码进寄存器：轨迹包含稳定段、缓慢越阈的真实报警段、阈值附近的随机抖动段和短促尖峰，并另存真实状态标签。对照 A 为单阈值报警，测量超过 $H$ 立即置位、回落到 $H$ 以下立即清除；对照 B 为迟滞报警，超过 $H_{on}$ 置位、低于 $H_{off}$ 才清除，且 $H_{off}<H_{on}$。比较轮询周期 $T_p\in\{100,250,500,1000\}$ ms。使用仓库示例中的 `SimDevice/SimData`，不要依赖 `ModbusDeviceContext` 的旧式接口；当前源码已标明后者在 v4 前会被移除。

可检验的研究问题是：**在同一条有标签的模拟寄存器轨迹、相同 TCP 服务端和相同异常帧位置下，迟滞报警相对单阈值报警能否在各轮询周期下减少错误状态翻转和错误报警驻留时间，同时把真实越阈事件的中位检测延迟与漏检率控制在预先冻结的范围内？** “轮询越快一定更好”与“迟滞一定更安全”都只是待验证假设。轮询过快可能增加通信请求而没有额外有效信息，迟滞也可能延后清除或检测边缘事件。

公平对照先以固定随机种子生成一份完整轨迹、事件标签和协议异常掩码，所有条件复用它们。服务端更新频率、寄存器地址、缩放系数、客户端超时、TCP 地址、运行时长和时钟记录方式均固定；条件只改变 $T_p$ 与单阈值/迟滞状态机。两类报警以相同初始状态启动，阈值在独立校准轨迹上一次性冻结，正式轨迹不得依据结果重调。若注入一次超时、非法地址或设备异常，应让所有条件在相同逻辑时刻接收相同掩码，并把协议失败与报警逻辑失败分开记录。

## 2026-10-26｜FreeRTOS-Kernel：优先级继承能否改善周期 PID 控制的尾部时延

推荐 [FreeRTOS/FreeRTOS-Kernel](https://github.com/FreeRTOS/FreeRTOS-Kernel)，把实践缩小为“一台主机上的 FreeRTOS POSIX 仿真：比较有优先级继承的互斥量与无优先级继承的二值信号量，在受控优先级反转下对周期 PID 控制任务时限和离散电机模型跟踪误差的影响”。这与当前 PID 学习中的 PWM、编码器反馈、离散采样和任务时间效率直接相连：控制律本身相同，但控制任务若不能准时获得 CPU 或共享日志缓冲区，就可能使实际采样周期偏离设计值。第一阶段只研究内核调度与合成离散对象，不能把结果外推为 STM32、真实电机、编码器或比赛机器人上的实时性结论。

固定源码参考 `main` 分支提交 `640d0c43705e64cd53f46b31d882de6cd8433933`。仓库现有能力的入口包括 [README](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/640d0c43705e64cd53f46b31d882de6cd8433933/README.md)、[CMake 配置](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/640d0c43705e64cd53f46b31d882de6cd8433933/CMakeLists.txt)、[任务接口](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/640d0c43705e64cd53f46b31d882de6cd8433933/include/task.h)、[信号量接口](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/640d0c43705e64cd53f46b31d882de6cd8433933/include/semphr.h)、[任务调度实现](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/640d0c43705e64cd53f46b31d882de6cd8433933/tasks.c)、[队列与互斥量实现](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/640d0c43705e64cd53f46b31d882de6cd8433933/queue.c) 与 [GCC POSIX 端口](https://github.com/FreeRTOS/FreeRTOS-Kernel/blob/640d0c43705e64cd53f46b31d882de6cd8433933/portable/ThirdParty/GCC/Posix/port.c)。README 明确说明本仓库只包含内核、头文件与端口，预配置演示工程在 `FreeRTOS/FreeRTOS` 的 `FreeRTOS/Demo` 下；因此本实践应自己新建很小的实验应用，而不是把内核误当作现成电机工程。CMake 已列出 `GCC_POSIX` 本机端口；`xTaskCreate()` 用于创建就绪任务，`xTaskDelayUntil()` 说明自身可用于固定执行频率且返回值可协助判断过期周期。`semphr.h` 说明二值信号量不使用优先级继承，`xSemaphoreCreateMutex()` 创建的互斥量使用优先级继承；`queue.c` 也实际调用 `xTaskPriorityInherit()` 与 `xTaskPriorityDisinherit()`。这些是仓库已有且已核验的能力，下面的离散对象、PID、负载任务、日志和实验结论均需学生新增。

实践只构造三个任务和一个简单的离散速度对象。高优先级控制任务每 $T=10$ ms 由 `xTaskDelayUntil()` 触发，读取模拟速度并计算带输出限幅的 PID；对象可先用

$$
\omega_{k+1}=a\omega_k+b u_k+d_k
$$

生成，其中 $r_k$ 是固定阶跃参考，$d_k$ 是预先保存的负载扰动。中优先级任务执行固定长度的计算负载；低优先级遥测任务在规定相位占有一个共享日志缓冲区。这样可人为形成“低优先级占锁、高优先级控制任务等待、中优先级任务插入执行”的优先级反转结构。条件 A 用 `xSemaphoreCreateBinary()` 作为无继承的共享门控基线，条件 B 用 `xSemaphoreCreateMutex()`；两条件都由同一个低优先级任务释放资源，且不从中断服务程序操作互斥量。这里的二值信号量条件只是用于构造无继承参考，不宣称它是生产代码中管理共享资源的首选方案。

可检验研究问题是：**在相同任务优先级、周期、共享临界区、计算负载、离散 PID、对象参数和扰动轨迹下，FreeRTOS 互斥量的优先级继承相对于二值信号量基线，是否降低高优先级控制任务的第 95/99 百分位锁等待时间与截止期错失率，并降低模拟速度闭环的积分绝对误差或超调？** “优先级继承一定改善控制效果”只是待验证假设。它可能显著改善尾部等待却对本对象的控制误差影响很小，也可能在没有中优先级负载时与基线几乎没有差异。

公平对照需要冻结内核提交、`FreeRTOSConfig.h`、抢占式调度配置、tick 频率、堆实现、三个任务优先级、栈深度、临界区代码、对象参数、PID 系数、参考轨迹、扰动种子、运行时长和时间戳位置。二值信号量在每次实验开始前显式置为可用，互斥量从未持有状态开始；正式运行中唯一改变的变量是同步原语。先在独立的校准负载集合上选定低优先级持锁工作量和中优先级计算工作量，使两种条件均能运行且至少一部分基线运行出现等待；正式集不得再据结果调工作量。每个正式扰动种子都在 A、B 两条件下配对运行至少 30 次，另设置“无中优先级负载”的阴性对照，以检查差异是否确由优先级反转而非普通锁开销产生。POSIX 端口仍受宿主机调度影响，需记录操作系统、编译器、CPU、后台负载和每次运行的原始时间戳；同一扰动的重复运行只能刻画计时抖动，不能被当成新的对象样本。

每个控制周期记录计划唤醒时刻、实际开始时刻、取锁前后时刻、实际采样间隔、控制输出、速度、参考值、任务运行时长和是否错过周期。主要调度指标为抖动 $j_k=t_k^{\mathrm{start}}-(t_0+kT)$、锁等待时间、第 95/99 百分位延迟、最大延迟、截止期错失率及控制任务被阻塞次数；闭环指标为

$$
\operatorname{IAE}=T\sum_k|r_k-\omega_k|,
$$

阶跃超调、进入并保持在预定误差带内的整定时间、输出饱和时间比例与最终稳态误差。应分别报告无中优先级负载和有负载条件，并保留所有错失周期和异常日志，不能只比较成功运行的平均值。若锁等待下降但 IAE 未变化，结论只能是本负载下调度尾延迟变化，不能扩展成电机性能一定提升。
